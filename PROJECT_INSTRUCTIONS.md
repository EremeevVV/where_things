# Инструкция проекта: навык Алисы «Где лежит вещь»

Этот документ — постоянный контекст проекта. Он кладётся в настройки проекта (project knowledge) и не меняется от итерации к итерации. Цель — чтобы на каждом новом шаге разработки не приходилось заново пересказывать суть, ограничения и текущее состояние.

## 1. Что мы делаем

Голосовой навык для Яндекс Алисы (в первую очередь — для Яндекс Станции). Пользователь голосом сообщает, куда положил вещь, навык это запоминает в памяти, привязанной к аккаунту. Позже пользователь голосом спрашивает, где лежит вещь, — навык отвечает.

Базовые сценарии:
- Запись: «запомни, что <вещь> лежит <место>» → сохранить пару (вещь, место).
- Поиск: «где лежит <вещь>?» → вернуть место или сказать, что не знает.
- Список: «что ты помнишь?» → перечислить вещи.
- Удаление: «забудь про <вещь>».

## 2. Архитектура и стек (зафиксировано)

- Навык = веб-сервис (вебхук), принимает POST JSON от Яндекс Диалогов, отвечает JSON.
- Backend: **Yandex Cloud Functions** (бесплатны для навыков Алисы, не тарифицируются).
- Язык: **Python** (если в ходе работы решим иначе — зафиксировать здесь).
- Хранилище данных: **Yandex Database (YDB) serverless**. Ключ пользователя — `session.user.user_id` (стабилен для авторизованных).
  - Таблица `items(user_id, name, place, updated_at)`.
- Консоль навыка: dialogs.yandex.ru → Навык в Алисе.

Почему YDB, а не встроенное хранилище Диалогов: встроенное `user_state` имеет жёсткий лимит **1 КБ**, чего может не хватить на список вещей. YDB снимает лимит и остаётся в той же бесплатной экосистеме.

## 3. Жёсткие ограничения платформы (помнить всегда)

- **Ответ навыка ≤ 4,5 секунды**, иначе сессия оборвётся. Держать соединение к YDB тёплым, запросы лёгкими.
- Память между сессиями работает **только для авторизованных через Яндекс ID**. На Станции пользователь всегда авторизован — основной кейс закрыт. Кейс неавторизованного («не могу запомнить надолго») обработать текстом.
- `session_state` (контекст внутри сессии) ≤ 1 КБ. Если не вернуть его в ответе во время многошагового диалога — контекст потеряется. Если состояние не меняется, но нужно сохранить — вернуть тот же объект, что пришёл.
- Текст ответа ≤ 5000 символов.
- Активационное имя НЕ должно содержать «Яндекс», «Алиса», «Станция», «открой», «запусти» и общеупотребительные слова. Нужны склонения и синонимы.
- После публикации Диалоги периодически пингуют навык; если он несколько часов молчит — отключат.

## 4. Три уровня хранения (не путать)

- `session_state` — внутри одной сессии (для уточняющих вопросов, машины состояний).
- `user_state` — между сессиями, только для авторизованных. Очистка — отправить `{}`.
- `application_state` — привязка к устройству, работает и для неавторизованных (запасной путь).

В нашем проекте долговременные данные → YDB; `session_state` → только для многошаговых диалогов.

## 5. NLU / разбор фразы

- Использовать `request.command`, `request.nlu.tokens`, `request.nlu.entities`.
- Выделять два слота: «вещь» и «место».
- Если пришла команда без слотов (например просто «запомни») — переспросить, сохранив шаг в `session_state` (машина состояний: ждём вещь → ждём место → подтверждаем).
- Сложные/нечёткие места («там, на полке у окна») — хранить как свободный текст, не пытаться чрезмерно нормализовать.

## 6. Структура ответа (эталон)

```json
{
  "response": {
    "text": "Запомнила: паспорт — верхний ящик стола.",
    "tts": "Запомнила: паспорт — верхний ящик стола.",
    "end_session": false
  },
  "version": "1.0"
}
```

## 7. Шаги развёртывания (чек-лист)

1. Yandex Cloud: облако + платёжный аккаунт (списаний за функции навыка нет).
2. Cloud Functions: создать функцию, runtime Python, загрузить обработчик.
3. YDB serverless: база + таблица `items`.
4. Консоль Диалогов: Создать диалог → Навык в Алисе.
5. Backend → «Функция в Яндекс Облаке» → выбрать функцию.
6. Включить «Использовать хранилище данных в навыке».
7. Активационное имя + склонения + синонимы.
8. Тип доступа → **Приватный** (даёт тест голосом на своей Станции без полной публикации).
9. Тест на вкладке Тестирование, затем голосом на колонке.

## 8. Как мы ведём разработку (важно)

Реализация почти наверняка не зайдёт с первой попытки. Поэтому:
- Работаем **итерациями**: одна итерация = одна проверяемая цель (эхо-навык → сохранение одной вещи → поиск → машина состояний → YDB → крайние случаи).
- После каждой итерации фиксируем в разделе 9 «Журнал»: что сделали, что сломалось, что меняем.
- Любое новое архитектурное решение записываем в этот файл, чтобы не потерять между сессиями.
- Код держим обозримым: один файл-обработчик, явные функции `handle_save`, `handle_find`, `handle_list`, `handle_delete`, парсер NLU отдельно.

## 9. Журнал итераций (заполняется по ходу)

- Итерация 0 — подготовка инструкции и вводного промта. Статус: готово.
- Итерация 1 — минимальный обработчик + эхо/приветствие, проверка на вкладке Тестирование. Статус: готово.
- Итерация 2 — NLU-парсер (SAVE/FIND/LIST/DELETE/UNKNOWN), сохранение/поиск в `session_state`, тесты (24 passed). Статус: готово.
- ...
